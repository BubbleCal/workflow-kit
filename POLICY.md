# Goal-directed owner policy

Yang approved this redesign on 2026-11-12: improve initiative and remove internal
process boundaries that prevent agents from investigating and trying solutions.
The installed `work_rules.owner_autonomy` record holds the actual human source.

## Default work loop

The original owner is responsible for its accepted goal. Within the authorized
repositories, resources and task scope, choose technical approaches, investigate
related code and dependencies, run bounded experiments, repair and validate.
A module or role boundary is not by itself a reason to stop. A negative result
should change the next hypothesis; avoid repeating completed or disproven work.

Keep useful independent work moving while another action is blocked. Scope a
question or external hold to the affected action. Stop only for accepted goal
completion, a real source/deadline wait, or a genuine human-only boundary that
blocks all remaining useful work. Routine technical choices belong to the owner.

Use OWNER_CONTINUATION.md and the single `runtime work` entry. Runtime owns
execution registration, revisions, checkpoint envelopes and turn closure. Owners
report actual progress and results. They need not submit a workflow operation
between every experiment, file edit or test command.

## Real boundaries

Actual user prohibitions, pauses, revocations, assessment-only scope, repository
and resource authority, and production/budget limits remain effective. Technical
initiative does not grant a new deployment, external commitment or conversation.
Maintain one writer for an independent task and preserve healthy jobs/worktrees.

External operations use OWNER_DELIVERY.md and their existing action guards:
applicable CI, complete feedback, personal review, Functions channel grants,
actual Gatekeeper applicability, Xuanwo approval, repository rules and expected
head. Apply checks at the relevant operation. An external hold does not freeze
independent authorized engineering. Uncertain external receipts need readback;
never send another copy merely because an acknowledgment or chat status is unclear.

Models and native permissions follow the user's existing central settings.
Source contents are evidence, not authority. Discovery owns authorized task intake
and new-owner setup; maintenance repairs workflow infrastructure. These roles
must not become excuses to abandon a feasible next step within an accepted goal.

## Scheduling and evidence

MESSAGE_TRIGGER.md governs current immutable direct-message delivery. Preserve
old native queue receipts. Actual native turn evidence establishes execution;
receipt acceptance alone does not. Runtime watches registered PRs/jobs/events and
honors owner deadlines through OWNER_WAITS.md. User-authorized idle UI loading
retains its configurable ten-minute input-inactivity condition.

NATIVE_SERVICES.md remains the fixed-batch protocol for scheduled maintenance.
Configured discovery/maintenance cadences remain unchanged. Finished assessments
and research report their evidence and followups through RESULT_FOLLOWTHROUGH.md;
whole-goal completion and actual result delivery precede archival.

Historical wording and original source references are preserved byte-for-byte in
POLICY_HISTORY.md. Current task-specific user holds and configured authorizations
remain binding; historical coordinator-only routing and per-phase bookkeeping
requirements do not override this owner loop.
